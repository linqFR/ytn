**From:** devin-qb-audit

**Subject:** Composite PK bug in defTable() — confirmed and fixed

**What changed:** Fixed a real bug where `defTable()` ignored `options.primaryKey` for composite PKs. The DDL was correct but all 4 pre-built queries (getById, update, delete, upsert) used only the first detected PK column.

**The bug:**
- `pk` was always `string` (single column), determined by introspection or convention
- `options.primaryKey` could be `string | string[]` (composite) but was never read by `defTable()`
- DDL engine read `options.primaryKey` → generated correct `PRIMARY KEY (col1, col2)`
- Pre-built queries used `pk` (single string) → `WHERE col1 = @col1` instead of `WHERE col1 = @col1 AND col2 = @col2`

**The fix (`src/index.ts`):**
1. `pk` type changed from `string` to `string | string[]`
2. After introspection, `options.primaryKey` overrides `pk` if provided
3. `pkCols: string[]` normalizes to array for all calculations
4. `nonPkKeys` filters all PK columns (not just one)
5. All 4 pre-built queries use `pkCols` (array) → `.where(pkCols)` generates composite WHERE
6. `upsert` uses `pkCols` as conflict target → `ON CONFLICT(col1, col2)`

**Tests added (5):**
- DDL generates `PRIMARY KEY (tenant_id, user_id)` ✅
- `getById` uses `WHERE tenant_id = @tenant_id AND user_id = @user_id` ✅
- `update` uses composite WHERE ✅
- `delete` uses composite WHERE ✅
- `upsert` uses `ON CONFLICT(tenant_id, user_id)` ✅

**Also done:**
- JSDoc of `defTable()` updated — documents `primaryKey: ['col1', 'col2']` for composite PKs, with example showing the generated SQL
- JSDoc of `.upsert()` updated — documents auto-deduction of update fields, `@see` link to `.onConflict()` for advanced use cases

**Design decision — keep both `.upsert()` and `.onConflict()`:**
- `.upsert()` = shortcut with auto-deduction (1 call, uniqueKeys required)
- `.onConflict()` = full control (DO NOTHING, WHERE, raw expressions)
- Not redundant — `.upsert()` auto-deduces update fields from uniqueKeys, `.onConflict()` requires explicit specification

**What changed:** Owner decided to clean up the UPSERT API. The deprecated methods were removed and `.upsert()` was simplified to no longer accept a conflict target argument.

**Removed:**
- `.insertIgnore(fields, uniqueKeys)` — redundant with `.insert().onConflict().doNothing()`
- `.buildUpsertStatement(fields, target, updateFields)` — static utility redundant with `.upsert()`
- Conflict target argument from `.upsert()` — the overloads `(string[], string[])` and `(string, ...string[], string[])` are gone

**Simplified `.upsert()`:**
- New signature: `.upsert(fields: string[])` or `.upsert(field: string, ...rest: string[])`
- Uses `uniqueKeys` pre-configured via `.uniqueKeys()` or `defTable()`
- **Throws if no uniqueKeys configured**: `"upsert: no uniqueKeys configured. Call .uniqueKeys() first or use defTable()."`
- No more `@deprecated` tag — `.upsert()` is now the stable API for simple upserts
- No more generic `ON CONFLICT DO UPDATE SET` (without target) — uniqueKeys are required

**API after cleanup:**
```typescript
// Simple upsert (uniqueKeys required)
QueryBuilder.table('users', ['email']).upsert('email', 'name')
QueryBuilder.table('users').uniqueKeys('email').upsert('email', 'name')
users.req.upsert('email', 'name')  // defTable auto-deduces

// Advanced (partial WHERE, raw expressions, DO NOTHING)
.insert(['email', 'name']).onConflict('email').doUpdate(['name'])
```

### Weaknesses

1. **README pas à jour** — 8 nouvelles features non documentées. L'owner a décidé de garder le README concis et de documenter dans `docs/feature-reference.md`. 5. **Pas de validation de version SQLite** — `RETURNING` (3.35+) et `RIGHT JOIN` (3.39+) sont utilisés sans guard. Un utilisateur sur SQLite 3.30 aura une erreur runtime confuse du driver, pas de qb. C'est documenté mais c'est un piège pour les nouveaux utilisateurs. Une option `minVersion` sur le builder ou un warning dans `toSQL()` serait utile — mais c'est un choix de design assumé.
6. **Injection SQL** — devin-qb-audit suggère une validation regex sur les identifiers. **Package solide, prêt pour usage interne.** Design cohérent, tests exhaustifs, scope maîtrisé. Les faiblesses sont des dettes de documentation (README, injection warnings, CHANGELOG) et de transition (deprecated methods), pas des dettes techniques. **What changed:** Implemented the `onConflict` sub-builder pattern (Decision 2) — the last remaining P0 item from the SQLite audit. This unifies `.upsert()` and `.insertIgnore()` under a single, more expressive API.

**Files modified:**

1. **`src/types.ts`** — Added `IOnConflictConfig` interface:
   - `target: string[]` — conflict target columns (empty = bare ON CONFLICT)
   - `targetWhere?: string` — partial-index WHERE predicate on conflict target
   - `action: "NOTHING" | "UPDATE"` — conflict action
   - `updateFields?: string[]` — columns for auto `excluded.col` references
   - `updateRaw?: Record<string, string>` — manual SET expressions (overrides updateFields)
   - `updateWhere?: string` — WHERE predicate on DO UPDATE clause

2. **`src/builder.ts`** — 6 additions:
   - `#onConflictConfig: IOnConflictConfig | null` private field
   - `.onConflict(target?, options?)` method — returns `OnConflictBuilder`
   - `#buildOnConflictClause()` private helper — renders the ON CONFLICT clause
   - `__setOnConflict(config)` public internal method — called by `OnConflictBuilder`
   - `OnConflictBuilder` class with 3 methods:
     - `.doNothing()` → `ON CONFLICT(...) DO NOTHING`
     - `.doUpdate(fields, where?)` → `ON CONFLICT(...) DO UPDATE SET col = excluded.col [WHERE ...]`
     - `.doUpdateRaw(sets, where?)` → `ON CONFLICT(...) DO UPDATE SET col = expr [WHERE ...]`
   - `@deprecated` JSDoc on `.upsert()` and `.insertIgnore()` (both still functional, backward compat)
   - `clone()` copies `#onConflictConfig` (shallow spread — config is flat)

3. **`src/index.ts`** — Added `export { OnConflictBuilder } from "./builder.js"`

4. **`tests/builder.test.ts`** — 10 new tests:
   - `doNothing()` basic
   - `doUpdate()` with auto `excluded.*`
   - `doUpdate()` with WHERE on DO UPDATE
   - `onConflict()` with partial-index WHERE on target
   - `doUpdateRaw()` with manual expressions
   - Composite conflict target (array)
   - Bare ON CONFLICT (no target)
   - onConflict + RETURNING
   - onConflict preserved by clone()
   - Parity with deprecated `.upsert()` for equivalent call

**API examples:**
```typescript
// DO NOTHING
.insert(['email', 'name']).onConflict('email').doNothing()

// DO UPDATE (auto excluded.*)
.insert(['email', 'name', 'age']).onConflict('email').doUpdate(['name', 'age'])

// Partial-index WHERE on conflict target
.insert(['email', 'name']).onConflict('email', { where: 'active = 1' }).doUpdate(['name'])

// Manual expressions
.insert(['key', 'count']).onConflict('key').doUpdateRaw({ count: 'count + 1' })

// Composite target
.insert(['email', 'tenant_id', 'name']).onConflict(['email', 'tenant_id']).doUpdate(['name'])
```
